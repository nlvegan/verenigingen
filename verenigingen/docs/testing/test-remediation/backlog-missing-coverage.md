## Module 6 — Membership/termination

- **Exclusive "default membership type" is enforced only client-side, not server-side** — from deleted `test_default_membership_type` (`membership_type/test_membership_type.py`). The deleted test explicitly documented (in a comment) that "the business logic for ensuring only one default doesn't appear to be implemented" and asserted two simultaneously-`default_for_new_members=1` Membership Types as the current (tautological — it asserts the flags it just set) behavior. Confirmed: `membership_type.py`'s `validate()` never references `default_for_new_members` at all — the ONLY enforcement is in `membership_type.js`'s `default_for_new_members(frm)` client-script handler, which prompts the user via `frappe.confirm()` and unsets the other type's flag via `frappe.client.set_value`. This is a **CLAUDE.md "business logic is server-side" violation**: any doc created via the REST API, Data Import, `bench console`/scripts, or the `members_without_dues_schedule` report's `{"default_for_new_members": 1}` filter can end up with multiple simultaneous defaults, since nothing server-side prevents it. If exclusivity is actually required, add a `validate()` guard in `membership_type.py` (unset any other type's flag, or throw) and replace the deleted test with a real assertion against that guard; otherwise leave as documented multi-default-allowed behavior.
