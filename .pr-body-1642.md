## What
Removing (or dropping a ptype from) a `CORE_GRANTS` tuple now revokes it on the next migrate. `CORE_GRANTS` is Python, so the #1629 `before_migrate` snapshot would already see the new list. Instead `_apply_core_grants` writes a ledger (`CORE_LEDGER_KEY`, a global default) of what it declared, `{doctype: {role: {"ptypes": [...], "defaults": [...]}}}`, and the next run lowers what the ledger holds and the current declaration does not.

Rules (never revoke what we did not grant):
- only the dropped flags, only on the (role, permlevel 0, not if_owner) row, every duplicate row at that key;
- never a flag the CURRENT stock DocPerm row for that role grants;
- flags nobody declared (admin edits, HRMS Employee Self Service `select`, Public Document Creator, ERPNext's Address/Accounts Manager) are never in the ledger, so they survive;
- a row with no stock counterpart is deleted once it carries no flag;
- `read` is never lowered while the tuple is still declared (write without read = edit a document you cannot open); it goes with the tuple (coordinator ruling);
- Frappe's creation defaults (read, export) on a row we created are ledgered apart from declared ptypes: they go with the tuple, unless the tuple declared them, in which case a later drop lowers them (export; read excepted above).
- an unparseable / wrongly shaped ledger is treated as empty (nothing revoked, re-seeded, `log_error`). The same guard is applied to the sibling #1629 snapshot in `_prune_revoked_keys`, which had the same unguarded `parse_json`.

Known divergence: a dropped DECLARED `export` is revoked, while an UNDECLARED `export` creation default stays while the tuple is kept (it goes with the tuple).
