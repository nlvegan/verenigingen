## 1. Current-state diagnosis (verified 2026-05-20)

### 1.5 The `reject_membership_application` divergence (audit said `:786`, actually `:738`)

`api/membership_application.py:738-780` is **not** a thin redirect like its `approve_membership_application` sibling at `:692-733`. It has its own implementation that:

1. Logs DEPRECATED warning (✓ same as approve sibling).
2. Checks `member.application_status not in ["Pending", "Under Review"]` — **DIVERGENT**.
3. Calls `member.reject_application(reason)` — which routes through `MemberLifecycleService.reject_application()` — the second orchestrator.
4. Calls `send_rejection_notification(member, reason)` directly (the canonical path does this too at `:615`).

**Compare to canonical `membership_application_review.reject_membership_application` (`:525-623`):**
- Valid-state check at `:556`: `["Pending", "Payment Failed", "Payment Cancelled", "Approved"]`. **Different set.**
- Notably accepts `"Approved"` (allows un-doing an approval) and `"Payment Failed"`/`"Payment Cancelled"` (payment-failure recovery), but **does NOT** accept `"Under Review"`.

This divergence is real and likely-unintentional: each set was written for its own context. Production JS only calls the canonical (`member.js:2854`, `membership_application_review.js:887`), so the deprecated shim's state-check set has been frozen since deprecation. Resolving the divergence is **out of scope** for this PR — see §6.

### 1.6 Concurrency-semantics gap (worth flagging)

The lifecycle service uses `SELECT ... FOR UPDATE` on `tabMember` (`member_lifecycle_service.py:112-117`, `:198-203`) to serialise concurrent approvals/rejections. The canonical path uses only `_handle_idempotent_approval()` which is a non-locking `frappe.db.get_value()` read. Two simultaneous canonical approves can in principle both pass the idempotency check before either commits.

**Real-world risk:** low. The canonical approval flow always runs in an HTTP request context with `@frappe.whitelist()` + `@high_security_api()`, and the page-level admin UI does not encourage rapid duplicate clicks. The `_handle_idempotent_approval` short-circuit catches the common case (page refresh → re-click). But the lifecycle service's tests in `test_concurrency_safety.py` *do* prove a stricter property.

**Decision:** This PR retires the FOR UPDATE-based lock along with the rest of the second orchestrator. If we want lock semantics on the canonical path later, that's a separate, opt-in change (`docs/audits` already documents `advisory_lock()` as the recommended pattern). The concurrency tests get repointed at the canonical path and adjusted to assert "at most one creates a membership" rather than "exactly one returns success" — see §5.

## 2. Recommended approach

**Option (a): Delete `MemberLifecycleService.approve_application()` + `reject_application()` + `_perform_post_*` helpers outright.**

### 2.1 Rationale

1. **The lifecycle path is dead in production.** Every JS/HTML caller, every page module, every internal Python caller already routes through `api.membership_application_review`. The only `Member.approve_application()` callers are tests and the deprecation wrapper.

2. **Option (b) "make lifecycle delegate to canonical" is a step backwards.** It preserves a 200-LOC wrapper for code that has no production users. Pure cost, no benefit.

3. **Option (c) "make canonical delegate to lifecycle" is wrong.** The canonical path is the production-blessed, security-decorated, chapter-permission-checked entry point. The lifecycle service was the *original* extraction and predates the consolidation done in `test_approval_unification.py`'s comment-block — that test file explicitly documents the lifecycle service's `approve_application` as deprecated-but-not-removed.

4. **One must-fix behavioural gap exists** (§1.6 + pending-chapter activation): the canonical sync path does NOT activate pre-existing pending `Chapter Member` records. The lifecycle service's `_perform_post_approval_setup` does. Before deletion we must move pending-chapter activation into the canonical path (it's a 15-LOC block). Without this, the integration tests at `test_chapter_membership_approval_integration.py:330` would regress real behaviour.

5. **The `Member.approve_application()` whitelisted endpoint can be removed too.** No production JS calls it; the canonical endpoint covers every UI use case. The `@frappe.whitelist()` removal is breaking-change-equivalent only to anyone calling it programmatically over HTTP, which we verified isn't happening.

### 2.2 What stays on `MemberLifecycleService` after retirement

After deleting `approve_application`, `reject_application`, `_validate_application_approval`, `_validate_application_rejection`, `_save_member_with_retry`, `_perform_post_approval_setup`, `_perform_post_rejection_cleanup`, only these methods are referenced:

| Method | External callers | Recommendation |
|---|---|---|
| `is_application_member` | `member.py:340-342` (delegates) + ~6 services | **Move to `member_status_service`**, drop the lifecycle delegation. |
| `update_membership_status` | zero callers (`Member.update_membership_status` delegates to `member_status_service` directly at `member.py:692-701`) | **Delete.** |
| `sync_status_fields` | zero callers (`Member.sync_status_fields` delegates to `member_status_service.sync_member_status_fields` at `member.py:507-513`) | **Delete.** |
| `get_status_color` | zero callers | **Delete.** |
| `_get_active_membership` / `_get_most_recent_expired_membership` | internal helpers for `update_membership_status` only | **Delete (with parent).** |

**Result:** `MemberLifecycleService` collapses to zero methods → **delete the entire file**. Move `is_application_member` (one-liner check on `application_id`) to `member_status_service.py`. The lazy singleton + module-level `__getattr__` shim go with it.

### 2.3 Behavioural-equivalence patch: pending-chapter activation in canonical path

Before deletion, add to `api/membership_application_review.approve_membership_application` (right after `_create_user_account_safe(...)` call, around current line `:500`):

```python
# Activate any pre-existing pending Chapter Member records
# (created at application-submission time via create_pending_chapter_membership)
from verenigingen.utils.application_helpers import activate_pending_chapter_membership
pending = frappe.db.sql(
    """SELECT parent AS chapter FROM `tabChapter Member`
       WHERE member = %s AND status = 'Pending'""",
    (member.name,),
    as_dict=True,
)
for row in pending:
    try:
        activate_pending_chapter_membership(member, row.chapter)
    except Exception as e:
        safe_log_error(
            "Pending chapter activation failed",
            f"Could not activate pending chapter {row.chapter} for {member.name}: {e}",
        )
```

This is lifted verbatim from `member_lifecycle_service.py:543-573`. Justification: this *is* the behaviour the integration tests assert — they're testing the right outcome via the wrong service.

## 5. Risk assessment

| Risk | Severity | Mitigation |
|---|---|---|
| **External HTTP caller hits `Member.approve_application` after deletion** | LOW | Verified zero production JS/HTML callers (§1.4). The function is whitelisted but undocumented externally. If a third-party integration exists (none found), they get a 404 with a clear "Method Not Allowed" — easy to debug. |
| **Concurrency regression: two parallel canonical approves both create memberships** | LOW–MED | Idempotency check in `_handle_idempotent_approval` catches the *common* case. Tight race window is real but tiny in practice (admin clicks Approve, request finishes, status flips to `Approved` before second click checks). If concrete evidence shows this happening, add `advisory_lock("member_approval:" + member_name)` as a follow-up — does not block this PR. |
| **Pending-chapter activation regression** | LOW | Caught by RED test in Step 1; behaviour explicitly added in Step 2 before any deletion. Step 4 repoints existing tests as guards. |
| **`is_application_member` import churn** | LOW | Only `member.py` calls the service-level function; all other callers use the instance method `member.is_application_member()` which doesn't change. Single grep-verified change. |
| **`test_concurrency_safety.py` was testing a property no longer available** | MED | The test gets *softened*, not deleted. The new assertion ("idempotency holds under load") is still a real safety property. Document in test docstring why the property changed. |

**Breaking-change surface:**
- 2 HTTP endpoints removed (`Member.approve_application`, `Member.reject_application`).
- 2 deprecated functions removed (`api.membership_application.approve_membership_application`, `api.membership_application.reject_membership_application`).
- 1 service module removed (`services.member.core.member_lifecycle_service`).
- 1 helper relocated (`is_application_member` → `member_status_service`).

**LOC delta estimate:**
- Deletes: ~647 (`member_lifecycle_service.py`) + ~95 (deprecated shims in `api/membership_application.py`) + ~74 (`Member.approve_application` + `Member.reject_application` in `member.py`) + ~190 test LOC = **~1006 LOC removed**.
- Adds: ~15 (pending-chapter activation in canonical) + ~15 (`is_application_member` move) + ~40 new RED tests + ~30 modified assertions in `test_approval_unification.py` = **~100 LOC added**.
- **Net: -~900 LOC.**

## 6. Out of scope (separate follow-up tickets)

These are noted by the audit but should NOT be bundled into this PR:

1. **`reject_membership_application` valid-state-check divergence (§1.5).** The canonical path's set `["Pending", "Payment Failed", "Payment Cancelled", "Approved"]` deserves a brainstorm — is rejecting an already-`Approved` member intentional UX? Is `"Under Review"` a real state worth honouring? **Separate ticket: `T4.1-followup-reject-state-checks`.** This PR removes the divergent shim so only one set survives, but does not relitigate which set is correct.

2. **`application_helpers.py` decomposition (1,510 LOC).** Mixes member creation, fee resolution, chapter state-machine, address creation. This PR touches `application_helpers.activate_pending_chapter_membership` and `remove_all_pending_chapter_memberships` only as imports — decomposing the rest is its own multi-PR effort. **Separate ticket: `T4.1-followup-application-helpers-split`.**

3. **`get_membership_type_details` logic split across two services.** Pure utility-function duplication, unrelated to orchestrator unification. **Separate ticket: `T4.1-followup-membership-type-details-dedup`.**

4. **Adding `advisory_lock()` to the canonical approval path.** Only if a concrete race-condition incident shows up post-merge. The existing idempotency guard plus the unique constraint on `Membership` (one Active per member) provide defence in depth.

5. **Member status service consolidation.** `MemberStatusService` and the about-to-arrive relocated `is_application_member` are good candidates for a deeper review but not blocking. **Separate ticket: `member-status-service-audit`.**
