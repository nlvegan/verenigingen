## What

`load_unpaid_invoices` and `load_unpaid_invoices_secure` refused every `limit` a browser sends. A form POST (what `frappe.call` sends) delivers values as text, and the validator checked `isinstance(limit, int)`.

Together with #2845 (#1220), this makes the Load Unpaid Invoices dialog work at all: #1220 made its failures visible, and this removes the one that fired on every load.

## Measured before the fix

Through the real WSGI app (werkzeug `Client(frappe.app.application)`, logged in with a session and CSRF token, user with the "Verenigingen System Administrator" role profile, test_site_4, no API keys): `"100"`, `"0"`, `"99999"`, `"abc"`, `"1.5"` and `""` all returned 400 "Invalid limit. Must be between 1 and 10000". Omitting `limit` returned 200. Not measured: a browser; the dialog's string `limit` rests on the form-POST measurement.

## Fix

`SEPAInputValidator.parse_batch_limit` returns an int in 1..10000 or raises the same `SEPAError` range message. It accepts ints and digit strings: optional sign, 1 to 20 ASCII digits (so `0000100` is 100), surrounding spaces or tabs. `None` still means "no limit". It refuses "abc", "1.5", "", "1e3", bool, float, Unicode digits, other whitespace and absurdly long digit runs.

Why not `limit: int` or `cint`: `cint("abc")` is 0 and `cint("1.5")` is 1, so garbage would be coerced rather than refused. An annotation also does not cover in-process callers. Both endpoints call the one helper, and the coerced int is what reaches the query and the "hit the limit" check.

The `_secure` twin had the identical bug and is fixed the same way.

## Tests

`verenigingen/tests/sepa/test_load_unpaid_invoices_limit_2843.py`: a WSGI class (subprocess, rows cleaned up) over both endpoints, plus in-process unit cases for the helper.

- Red without the fix: `Ran 8 tests ... FAILED (failures=6, errors=24)`. The 6 failures are the digit-string limits returning 400 on both endpoints; the 24 errors are the missing helper.
- Green with the fix: `Ran 8 tests ... OK`.
- Mutant `cint(limit)` + range check: 8 failures ("1.5", "1e3", 1.5, 100.0, `True`, Arabic digits). The reviewer's 3 wrong-fix mutants also reddened.

## Sweep

`isinstance(x, int)` across non-test code: 7 hits. Two are these endpoints. The rest (`source_folder_backfill`, `optimized_queries`, `setup`, `termination_operations`, `eboekhouden_clean_reimport`) are internal and not browser-reachable. Other whitelisted numeric SEPA/payments parameters are annotated `int`, so Frappe coerces them. No further instances, so no new issue.

## Review

Independent review: approved with nits.

1. `parse_batch_limit("9" * 5000)` raised an uncaught `ValueError` (4300-digit limit): the digit run is now bounded to 20, and a unit case covers 5000 digits.
2. `\s*` accepted any Unicode whitespace (`"\xa05"`, `"1\n"`): narrowed to `[ \t]*`, with cases showing both are refused.
3. The accepted forms (`+5`, `0000100`, surrounding spaces) are documented in the docstring and covered by tests.

Closes #2843
